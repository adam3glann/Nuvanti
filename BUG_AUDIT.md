# Nuvanti bug audit

Audit started 2026-10-13. Findings are added as they are confirmed. “Fixed” means code was changed in this audit; runtime/database verification remains pending unless stated.

## Confirmed findings

| # | Finding | Location | Status |
|---|---|---|---|
| 1 | Unpaid InstaPay orders reserved inventory forever. | `backend/lib/orderLifecycle.js`, `backend/server.js` | Fixed: expire after 24 hours, restore stock and discount use; added migration index `039_instapay_order_expiry.sql`. |
| 2 | Unpaid Paymob guest checkout could send a misleading order-confirmation email before payment. | `backend/routes/orders.js` | Fixed: checkout confirmation is sent only for COD; Paymob confirmation follows successful callback, InstaPay confirmation follows manual verification. |
| 3 | Manual InstaPay verification did not send the customer a payment confirmation. | `backend/routes/admin.js` | Fixed: send paid status email with tracking link. |
| 4 | Store-data reset erased all previous audit history. | `backend/routes/admin.js` | Fixed: reset preserves audit logs and records the reset action. |
| 5 | If Paymob checkout setup failed after account creation, the customer had an account but no verification email or clear recovery path. | `backend/routes/orders.js` | Fixed: issue the account session, send verification, and return a specific recovery message. |
| 6 | Concurrent address creates/updates marked “default” can leave multiple default addresses, and a failed insert/update after clearing the old default can leave the customer with no default address. The clear-and-write steps are separate non-transactional queries and the schema has no one-default-per-user constraint. | `backend/routes/addresses.js` | Fixed: make the operations transactional and enforce a single default per user. |
| 7 | Checkout accepts a missing color for a color-variant product, then decrements stock for the first color but stores `NULL` as the order-item color. On cancellation/expiry, inventory restoration cannot find that variant key, so that stock stays missing and the order loses its selected-color record. | `backend/routes/orders.js`, `backend/lib/orderLifecycle.js` | Fixed: require a selected color whenever the product has color variants, and persist the resolved variant. |
| 8 | Deleting a category or collection does not update products that reference its slug. Products become attached to a nonexistent taxonomy entry and can disappear from category/collection browsing while remaining active. | `backend/routes/admin.js` category/collection DELETE routes | Fixed: reject deletion while products are assigned, or atomically reassign/clear references. |
| 9 | Editing product colors can make variant stock inconsistent. `PATCH /products/:id` preserves the old `inventoryByVariant` map even when colors change; `productInventory()` falls back to the entire size total for a new first color while retaining counts for any old matching colors. Checkout then may expose/infer stock for variants that do not match the saved stock map, causing overselling or inaccessible units. | `backend/routes/admin.js`, `backend/lib/catalog.js` | Fixed: reconcile variant stock when color/size options change, or reject option edits until stock is explicitly mapped. |
| 10 | The Admin Inventory page inserts product name, color, size, and SKU into `innerHTML` without escaping. A crafted catalog value can execute stored JavaScript when an administrator opens Inventory. | `frontend/admin/assets/js/pages/inventory.js` (row rendering) | Fixed: HTML-escape all catalog text before interpolation. |
| 11 | Hard-deleting a product that appears in historical `order_items` violates the database foreign key (`product_id` has no delete cascade), but the endpoint does not catch that constraint and returns a generic 500. The product delete control therefore fails unexpectedly for any product with order history. | `backend/routes/admin.js` product DELETE route; `backend/migrations/001_init.sql` | Fixed: archive products or return a deliberate conflict response that explains the order-history restriction. |
| 12 | The Admin Orders page fetches only the latest 100 orders and performs search, filtering, and pagination in the browser. Older orders become impossible to find/open from that page once the store has more than 100 orders. | `backend/routes/admin.js` `/orders` default limit; `frontend/admin/assets/js/services/orderService.js` | Fixed: add server-side search/filter/pagination or load the complete order set safely. |
| 13 | Analytics computes the “Paid Orders” KPI from a series count that includes every non-cancelled order, including unpaid orders. The displayed paid-order count is overstated. | `backend/routes/admin.js` `/analytics`; `frontend/admin/assets/js/pages/analytics.js` | Fixed: count orders meeting the paid/fulfilled revenue rule, or relabel the KPI as non-cancelled orders. |
| 14 | Custom delivery locations derive IDs from a slugified name, but collisions are not detected. Names such as `New Cairo` and `New-Cairo` produce the same ID; checkout then resolves either selection to the first location and can charge the wrong shipping price. | `frontend/admin/assets/js/pages/settings.js`, `backend/routes/admin.js` settings validation, `backend/routes/orders.js` location lookup | Fixed: ensure IDs are unique on save (and reject duplicate IDs server-side). |
| 15 | Cart and order-success state rely on `localStorage`/`sessionStorage` writes without handling storage exceptions. Most critically, `createOrder()` can successfully create a server-side order, then reject when saving the returned order to `sessionStorage`; checkout reports an error and allows retry, risking a duplicate order. If `localStorage` writes fail, cart actions also throw. | `frontend/assets/js/services/orderService.js`, `frontend/assets/js/services/cartService.js` | Fixed: make browser storage best-effort and never turn a confirmed server order into a checkout failure. |
| 16 | Restoring a backup silently invalidates every newsletter unsubscribe link already sent to subscribers. The backup omits `unsubscribe_token_hash`, and restore assigns each subscriber a new random hash without sending a replacement unsubscribe link. Existing emails then receive an “invalid” response and the subscriber cannot unsubscribe using the link in their email. | `backend/routes/admin.js` backup export; `backend/lib/maintenanceBackup.js` restore | Fixed: preserve unsubscribe capability securely (for example, reissue links after restore or preserve the hashed tokens in protected backups). |
| 17 | Variant stock keys concatenate color and size with `::`, but product validation allows that delimiter inside either value. Distinct variants such as color `Red::M` / size `L` and color `Red` / size `M::L` produce the same key, so one stock value overwrites the other and checkout/inventory can show or deduct the wrong variant quantity. | `backend/routes/admin.js` product schema; `backend/lib/catalog.js`; `backend/routes/orders.js` | Fixed: reject `::` in color/size values or use an unambiguous encoded/structured key format consistently. |
| 18 | Customer login/registration can succeed on the server and set the session cookie, then throw while saving the display session to `localStorage`. The page reports authentication failure even though the browser is signed in; `getCurrentUser()` can similarly reject after receiving a valid session. | `frontend/assets/js/services/authService.js` | Fixed: treat the local display cache as optional and catch storage errors, as the server cookie is the authentication authority. |
| 19 | Admin product-list requests are not sequenced or cancelled. If a search/filter request is slow and a newer one finishes first, the old response can replace the newer results while the controls still show the newer query. Periodic live refreshes can cause the same race. | `frontend/admin/assets/js/pages/products.js` `load()` | Fixed: ignore responses whose request ID is no longer current, matching the storefront catalog page’s guard. |
| 20 | Other Admin list pages have the same request/state race: Customers and Inventory can display stale responses over newer filters. Orders uses a `loading` boolean that drops any search/filter request made while the previous request is still running; the old result is then rendered under the new controls until another refresh. | `frontend/admin/assets/js/pages/customers.js`, `frontend/admin/assets/js/pages/inventory.js`, `frontend/admin/assets/js/pages/orders.js` | Fixed: sequence requests and ensure a state change during an in-flight request triggers a fresh load. |
| 21 | Admin Products and Inventory pages make nonessential summary/filter requests before wiring or loading their primary list. If category loading (`products.js`) or inventory statistics (`inventory.js`) fails, the unhandled rejection stops initialization, so the actual product/stock list and its controls never load even if their own API endpoint is healthy. | `frontend/admin/assets/js/pages/products.js` `init()`; `frontend/admin/assets/js/pages/inventory.js` `init()` | Fixed: handle these auxiliary requests independently and continue initializing the main list with an inline warning/fallback. |
| 22 | Backup restore preserves destination staff accounts but inserts restored customers with their source `users.id` values. A staff account in the destination with one of those IDs causes a primary-key conflict and aborts the entire restore transaction. | `backend/lib/maintenanceBackup.js` customer insert; `backend/routes/admin.js` backup export/restore | Fixed: remap restored customer IDs and their order/address references, or validate/report ID conflicts before destructive restore work. |
| 23 | Editing a category slug does not update the `products.category` references. The Admin explicitly tells the operator existing products keep the old category, but the old slug no longer resolves to an active category; those products disappear from the category’s browse page/filter and can appear uncategorized to customers. | `frontend/admin/assets/js/pages/catalog.js` category editor; `backend/routes/admin.js` category PATCH | Fixed: update linked product category slugs transactionally, or prevent slug changes while products are assigned and offer a migration action. |
| 24 | Admin’s global search advertises orders, products, customers, and SKUs, but Enter always sends the text to the Products page, whose search only matches product name/SKU. Searching for an order number or customer name/email therefore returns no relevant result. | `frontend/admin/assets/js/components/header.js`; `frontend/admin/assets/js/pages/products.js` | Fixed: implement entity-aware global results or make the control’s label and behavior accurately product-only. |
| 25 | Cart line IDs concatenate product ID, size, and color with `__`, while product option validation permits `__` inside option names. Distinct variants can then share one line ID; adding one can merge quantities and overwrite the displayed color/size, causing the customer to order a different variant than selected. | `frontend/assets/js/services/cartService.js` | Fixed: encode each component unambiguously (or use a stable opaque line ID) and migrate existing cart records safely. |
| 26 | The cart drawer’s increment button is disabled only at quantity 10, not when selected variant stock is exhausted. The click is then silently capped by `updateQuantity()`, leaving an apparently active button that does nothing; the full cart page already checks stock correctly. | `frontend/assets/js/components/cartDrawer.js` | Fixed: use the same stock-aware `canIncreaseQuantity()` check as the cart page. |

## Review progress

- Backend auth, DB setup, payment callback, migration runner, contact/newsletter/navigation/storefront/upload routes, maintenance backup/restore, checkout/account flows, Admin list/settings/content flows, load-test scripts, deployment config, and local HTML asset references reviewed.
- Twenty-one additional confirmed defects are recorded above, including backup/restore failures, category slug orphaning, ambiguous variant/cart keys, misleading Admin search, and several Admin list initialization/race issues. Each has a code fix in this working tree; database-backed and browser flows remain unverified.
- The 26 confirmed findings in this ledger have code changes recorded as fixed. The project-wide review is still not exhaustive: remaining Admin/customer pages, shared components, static policy pages/assets, and deeper route-to-UI edge cases still need inspection.
- Local HTML asset-reference scan found no missing referenced JS, CSS, image, or font files. No database-backed flow was run.
